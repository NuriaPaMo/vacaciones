# Use Case: Cancel Vacation Request

## Metadata

| Property      | Value                                  |
| ------------- | -------------------------------------- |
| UC ID         | UC-003                                 |
| User Story    | US-003                                 |
| Feature       | F-001 (gh#2)                           |
| Primary Actor | Employee                               |
| Scope         | Vacation Request Management            |
| Level         | User Goal                              |
| Status        | Draft                                  |

## Brief Description

An employee cancels a vacation request they previously submitted. Pending requests are cancelled
directly; approved requests require explicit confirmation. The system updates the request status,
creates an audit trail entry, recalculates capacity if needed, and notifies affected approvers.

## Stakeholders and Interests

| Stakeholder        | Interest                                                    |
| ------------------ | ----------------------------------------------------------- |
| Employee           | Ability to withdraw a request when plans change             |
| Project Manager    | Know when a team member cancels so they can re-plan         |
| Department Manager | Capacity recalculation after cancellation                   |
| System             | Maintain data integrity and correct capacity snapshots      |

## Preconditions

1. Employee is authenticated via Entra ID
2. A vacation request in status Pending or Approved exists for this employee
3. The request belongs to the authenticated employee

## Postconditions (Success Guarantees)

1. VacationRequest status updated to Cancelled
2. StatusTransition record created with actor = employee, timestamp = now
3. Capacity snapshot recalculated for affected dates
4. Notification published to Service Bus (email to approvers via F-006)

## Triggers

- Employee clicks "Cancel" button on a request in "My Requests" or request detail view

---

## Main Success Scenario (Basic Flow) — Pending Request

| Step | Actor          | System                                                         |
| ---- | -------------- | -------------------------------------------------------------- |
| 1    | Employee clicks "Cancel" on a Pending request |                                     |
| 2    |                | System updates request status to Cancelled                     |
| 3    |                | System creates StatusTransition: Pending → Cancelled           |
| 4    |                | System publishes RequestCancelled event to Service Bus         |
| 5    |                | System shows success: "Request cancelled successfully"         |
| 6    |                | System updates the request row in the list (greyed out badge)  |

---

## Alternative Scenario — Approved Request

| Step | Actor                   | System                                                    |
| ---- | ----------------------- | --------------------------------------------------------- |
| 1    | Employee clicks "Cancel" on an Approved request |                              |
| 2    |                         | System shows confirmation dialog: "This request is already approved. Are you sure you want to cancel it?" |
| 3    | Employee clicks "Confirm Cancel" |                                                  |
| 4    |                         | System updates status to Cancelled                        |
| 5    |                         | System creates StatusTransition: Approved → Cancelled     |
| 6    |                         | System publishes RequestCancelled event (triggers notifications to PM and DM) |
| 7    |                         | System recalculates capacity snapshots for affected dates |
| 8    |                         | System shows success confirmation                         |

## Extensions (Alternative Flows)

### 1a. Request Already Cancelled or Rejected

| Step  | Actor          | System                                                      |
| ----- | -------------- | ----------------------------------------------------------- |
| 1a.1  |                | "Cancel" button is not rendered for Cancelled/Rejected requests |
| 1a.2  | Employee cannot trigger the action                                              |

### 3a. Employee Dismisses Confirmation Dialog

| Step  | Actor                    | System                                             |
| ----- | ------------------------ | -------------------------------------------------- |
| 3a.1  | Employee clicks "Keep Request" in dialog |                                    |
| 3a.2  |                          | System closes dialog; request remains Approved     |

### \*a. System Unavailable

| Step  | Actor          | System                                                      |
| ----- | -------------- | ----------------------------------------------------------- |
| \*a.1 |                | System returns 503; frontend shows error and preserves request status |

## Special Requirements

- **Security**: Employee can only cancel their own requests
- **Audit**: Every cancellation creates a StatusTransition record
- **Idempotency**: Double-clicking Cancel must not create two cancellations
- **Performance**: API response < 300ms (P95)

## Technology and Data Variations

- **ServiceNow**: If request was already exported to ServiceNow, a removal message is published (handled by F-005)

## Frequency of Occurrence

- Expected: ~5% of requests cancelled = ~100 cancellations/year
- Peak: Before summer season (employees re-planning)
