## Brief Description

An authenticated employee selects vacation dates through a visual calendar interface and submits a
formal vacation request. The system validates the dates, calculates business days, checks for
overlapping requests, and creates the request in Pending status.

## Stakeholders and Interests

| Stakeholder        | Interest                                                  |
| ------------------ | --------------------------------------------------------- |
| Employee           | Submit vacation request quickly with immediate confirmation |
| Project Manager    | Receive notification of new request for review            |
| System             | Enforce business rules and maintain data integrity        |
| Compliance         | Audit trail of all requests with timestamps               |

## Preconditions

1. Employee is authenticated via Entra ID (SSO)
2. Employee has the "Employee" role in the system
3. Employee does not have an overlapping Pending or Approved request for the same dates
4. Start date is at least 1 business day in the future

## Postconditions (Success Guarantees)

1. VacationRequest record created in database with status = Pending
2. Request ID assigned and returned to the employee
3. Total business days calculated and stored
4. StatusTransition record created (null → Pending)
5. Approval workflow triggered (notification to Project Manager)

## Triggers

- Employee navigates to "New Request" or "Submit Vacation" action in the application

## Main Success Scenario (Basic Flow)

| Step | Actor          | System                                                      |
| ---- | -------------- | ----------------------------------------------------------- |
| 1    | Employee opens the vacation request form |                                              |
| 2    |                | System renders the date picker calendar highlighting unavailable dates |
| 3    | Employee selects start date on the calendar |                                          |
| 4    |                | System highlights the selected start date                   |
| 5    | Employee selects end date on the calendar |                                            |
| 6    |                | System highlights the selected range and shows total business days |
| 7    | Employee optionally adds notes/comments (max 500 chars) |                              |
| 8    | Employee clicks "Submit Request" |                                                    |
| 9    |                | System validates: dates not in past, start < end, no overlap, sufficient balance |
| 10   |                | System calculates total business days (Mon–Fri, excluding weekends) |
| 10a  |                | System checks employee vacation balance ≥ total days requested |
| 11   |                | System persists VacationRequest with status = Pending       |
| 12   |                | System creates StatusTransition record                      |
| 13   |                | System publishes RequestSubmitted event to Service Bus       |
| 14   |                | System returns success confirmation with Request ID and summary |

### Detailed Steps

**Step 9 — Validation**

- Validates: start date ≥ today + 1 business day (BR-002, CL-001 confirmed)
- Validates: start date < end date (BR-001)
- Validates: no existing Pending/Approved request overlapping the date range (BR-004)
- Validates: employee vacation balance ≥ requested days (BR-006c, CL-013 confirmed)

**Step 10 — Business Day Calculation**

- Counts Mon–Fri days only between start and end (inclusive) (BR-003)

**Step 13 — Event Publication**

- Event triggers: email notification to Project Manager (F-006)

## Special Requirements

- **Performance**: API response < 300ms (P95)
- **Security**: JWT Bearer token required; employee can only submit for themselves
- **Audit**: StatusTransition record created for every request
- **Accessibility**: Calendar picker must be keyboard-navigable (WCAG 2.1 AA)

## Technology and Data Variations

- **Date Format**: ISO 8601 (YYYY-MM-DD) in API; localized display in UI
- **Timezone**: All dates stored in UTC; displayed in user's local timezone
- **Weekend Handling**: Weekends excluded from business day calculation

## Frequency of Occurrence

- Expected: ~4 requests/employee/year × 500 employees = ~2,000 requests/year
- Peak: ~200 requests/week during summer pre-season (May–June)
