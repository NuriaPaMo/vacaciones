## Brief Description

A background scheduler periodically checks all pending approval requests. When a request has been
waiting beyond the configured reminder threshold, it sends a reminder to the approver. When it
exceeds the escalation threshold, it alerts the Department Manager and grants them authority to
bypass project-level approval.

## Stakeholders and Interests

| Stakeholder        | Interest                                                       |
| ------------------ | -------------------------------------------------------------- |
| Scheduler (System) | Execute reliably every 30 minutes without missed escalations   |
| Project Manager    | Receive reminders before escalation occurs                     |
| Department Manager | Be alerted when PM action is overdue                           |
| Employee           | Request not stalled indefinitely                               |
| Compliance         | EscalationEvent records all triggers                           |

## Preconditions

1. Background job (Azure BackgroundService) is running
2. EscalationThreshold configuration exists (reminder days, escalation days)
3. VacationRequests in Pending status exist with CurrentApprovalLevel = Project

## Postconditions (Success Guarantees — Reminder)

1. EscalationEvent record created: Type=Reminder, RequestId, TriggeredAt
2. Reminder email sent to PM (via F-006)

## Postconditions (Success Guarantees — Escalation)

1. EscalationEvent record: Type=Escalation, RequestId, TriggeredAt
2. Alert email + Teams message sent to DM (via F-006)
3. VacationRequest flagged as Escalated (DM can now act directly)

## Triggers

- Scheduler job runs every 30 minutes and scans all pending requests

---

## Main Success Scenario — Escalation Triggered

| Step | Actor                   | System                                                         |
| ---- | ----------------------- | -------------------------------------------------------------- |
| 1    | Scheduler fires every 30 minutes |                                                       |
| 2    |                         | System queries all VacationRequests with Status=Pending AND CurrentApprovalLevel=Project |
| 3    |                         | For each: calculates business days since LastStatusChangeAt    |
| 4    |                         | If days ≥ reminder threshold (default 3): check if reminder already sent |
| 5    |                         | If reminder not sent: create EscalationEvent(Reminder), publish event |
| 6    |                         | If days ≥ escalation threshold (default 5): create EscalationEvent(Escalation) |
| 7    |                         | System flags VacationRequest.IsEscalated = true               |
| 8    |                         | System publishes EscalationAlert event → DM notified          |
| 9    |                         | DM can now approve/reject the request directly                |

## Extensions (Alternative Flows)

### 4a. Reminder Already Sent

| Step  | Actor          | System                                                       |
| ----- | -------------- | ------------------------------------------------------------ |
| 4a.1  |                | System detects EscalationEvent(Reminder) already exists for this request |
| 4a.2  |                | System skips duplicate reminder; continues to check escalation threshold |

### 6a. Request Approved Before Escalation Check

| Step  | Actor          | System                                                       |
| ----- | -------------- | ------------------------------------------------------------ |
| 6a.1  |                | System detects request status is no longer Pending           |
| 6a.2  |                | System skips the request (no escalation needed)              |

### 2a. No Pending Requests

| Step  | Actor          | System                                                       |
| ----- | -------------- | ------------------------------------------------------------ |
| 2a.1  |                | Query returns empty; job logs "No pending requests" and exits |

### \*a. Notification Service Unavailable

| Step  | Actor          | System                                                       |
| ----- | -------------- | ------------------------------------------------------------ |
| \*a.1 |                | Event published to Service Bus; notification retry handled by F-006 |

## Special Requirements

- **Idempotency**: Running the job twice in a row must not send duplicate reminders
- **Business Days**: Threshold calculation uses business days only
- **Observability**: Each job run logged to Azure Monitor with: requests checked, reminders sent, escalations triggered
- **Configuration**: Thresholds changeable via admin panel (F-007) without restart

## Technology and Data Variations

- **Scheduler**: .NET BackgroundService with periodic timer (every 30 min)
- **Locking**: Distributed lock (Redis) prevents concurrent runs

## Frequency of Occurrence

- Job runs: every 30 min = 48 times/day
- Average escalations triggered: 2-5/week
