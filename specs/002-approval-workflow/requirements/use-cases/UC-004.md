## Brief Description

A Project Manager reviews pending vacation requests from their team members, assesses coverage
impact, and approves or rejects each request. Approval advances the request to Department-level
review; rejection is final and notifies the employee with a mandatory reason.

## Stakeholders and Interests

| Stakeholder        | Interest                                                     |
| ------------------ | ------------------------------------------------------------ |
| Project Manager    | Efficient queue management; avoid coverage gaps in project   |
| Employee           | Fast decision, clear reason if rejected                      |
| Department Manager | Receives only project-approved requests for final review     |
| System             | Route request correctly and maintain workflow state          |

## Preconditions

1. Project Manager is authenticated via Entra ID with the "ProjectManager" role
2. At least one VacationRequest in status Pending exists for an employee in the PM's project
3. No active delegation covers this PM's authority

## Postconditions (Success Guarantees — Approve)

1. ApprovalStep record created: Level = Project, Status = Approved
2. VacationRequest.CurrentApprovalLevel advances to Department
3. Notification published → Department Manager alerted (F-006)

## Postconditions (Success Guarantees — Reject)

1. ApprovalStep record created: Level = Project, Status = Rejected, Reason = [provided]
2. VacationRequest status = Rejected (final)
3. Notification published → Employee notified of rejection with reason (F-006)

## Triggers

- PM clicks "Approve" or "Reject" on a request in the Approval Queue
- PM clicks an action link received via email notification

## Main Success Scenario — Approve

| Step | Actor                  | System                                                        |
| ---- | ---------------------- | ------------------------------------------------------------- |
| 1    | PM navigates to "Approval Queue" |                                                     |
| 2    |                        | System fetches all Pending requests for PM's project members  |
| 3    |                        | System renders queue: employee name, dates, days, capacity impact |
| 4    | PM reviews a request and clicks "Approve" |                                       |
| 5    |                        | System creates ApprovalStep (Level=Project, Status=Approved)  |
| 6    |                        | System updates VacationRequest.CurrentApprovalLevel = Department |
| 7    |                        | System publishes RequestProjectApproved event                 |
| 8    |                        | System removes request from PM's queue                        |
| 9    |                        | System shows: "Request approved and sent to department review" |

### Reject Scenario

| Step | Actor                  | System                                                        |
| ---- | ---------------------- | ------------------------------------------------------------- |
| 4    | PM clicks "Reject"     |                                                               |
| 5    |                        | System shows rejection reason text area (mandatory)           |
| 6    | PM enters reason (min 10 chars) and confirms |                                    |
| 7    |                        | System validates reason is provided                           |
| 8    |                        | System creates ApprovalStep (Level=Project, Status=Rejected, Reason=…) |
| 9    |                        | System updates VacationRequest status = Rejected              |
| 10   |                        | System publishes RequestRejected event → employee notified    |

## Extensions (Alternative Flows)

### 6a. Reject Without Providing a Reason

| Step  | Actor          | System                                                       |
| ----- | -------------- | ------------------------------------------------------------ |

| 6a.2  |                | System shows inline error: "Rejection reason is required (min 10 chars)" |

### 3a. Capacity Warning on Request

| Step  | Actor          | System                                                       |
| ----- | -------------- | ------------------------------------------------------------ |
| 3a.1  |                | System detects the request overlaps a period ≥ 65% capacity  |
| 3a.2  |                | System renders an orange warning badge on that row           |
| 3a.3  | PM sees warning before deciding |                                               |

### \*a. PM Has Active Delegation

| Step  | Actor          | System                                                       |
| ----- | -------------- | ------------------------------------------------------------ |
| \*a.1 |                | System also shows the queue to the delegate                  |
| \*a.2 | Delegate approves/rejects on behalf                                              |
| \*a.3 |                | ApprovalStep records both ActorId = Delegate and DelegatedById = PM |

## Special Requirements

- **Performance**: Approval action API < 300ms (P95)
- **Security**: PM can only act on requests from their project members
- **Audit**: ApprovalStep immutably records actor, timestamp, decision, reason
- **Mobile**: Approval queue must be responsive for mobile use

## Technology and Data Variations

- **Delegation**: If delegate acts, both IDs stored in ApprovalStep

## Frequency of Occurrence

- Expected: ~5-10 approvals/PM/week peak season
- Peak: ~200 PM approvals/week (summer)
