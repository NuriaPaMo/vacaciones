5. Arquitectura Propuesta

Basándose en los requisitos y conceptos identificados, se propone la siguiente arquitectura:

5.1 Estilo Arquitectónico

Para avanade se recomienda una arquitectura web en capas con enfoque modular, desplegada en Microsoft Azure, compuesta por una aplicación frontend en Vue, una API de negocio y un módulo de integración con sistemas corporativos externos.

El estilo propuesto es monolito modular como punto de partida, porque el alcance funcional identificado se concentra en un único dominio principal: gestión y aprobación de vacaciones. Este enfoque permite entregar antes, reducir complejidad operativa y mantener separadas las responsabilidades internas del sistema sin introducir el coste de microservicios.

La arquitectura debe contemplar integraciones asíncronas o programadas para la carga nocturna de datos, dado que se indica explícitamente que no se requiere sincronización en tiempo real. Esto aplica especialmente a la obtención de información desde Active Directory y ServiceNow, así como al envío del listado de vacaciones aprobadas a ServiceNow.

5.2 Capas del Sistema

  • Capa de presentación
    Aplicación web desarrollada en Vue, accesible mediante un enlace en una primera etapa. Debe cubrir consulta de calendarios, visualización de periodos sobresolicitados, revisión de solicitudes y acciones de aprobación, rechazo o cancelación según el rol.
  • Capa de aplicación / API
    Expone los casos de uso del sistema: alta y consulta de solicitudes, aprobación a nivel de proyecto y departamental, rechazo, cancelación, consulta histórica, notificaciones y reglas de validación sobre cupos o periodos.
  • Capa de dominio
    Contiene la lógica de negocio de vacaciones: solicitudes, estados, flujo de aprobación, responsables, delegación, jerarquía organizativa, periodos configurables en días o semanas y reglas para identificar sobresolicitación.
  • Capa de integración
    Encapsula el acceso a Active Directory para estructura organizativa y pertenencia, a ServiceNow para datos de departamento y para el envío de vacaciones aprobadas, y a los canales de notificación por correo electrónico y opcionalmente Teams.
  • Capa de persistencia
    Base de datos transaccional para solicitudes, aprobaciones, cancelaciones, delegaciones, trazabilidad de estados, configuración de periodos y resultados de sincronizaciones nocturnas.
  • Procesos batch y tareas programadas
    Responsables de la descarga nocturna de actualizaciones, consolidación de datos organizativos desde fuentes externas y preparación del listado de vacaciones aprobadas a enviar a ServiceNow.
  • Capa de seguridad y acceso
    Gestión de autenticación y autorización basada en roles organizativos, diferenciando al menos usuario solicitante, responsable de proyecto y responsable departamental, de acuerdo con los requisitos funcionales identificados.

5.3 Justificación

  • Ajuste al volumen
    Con un objetivo de 500 usuarios concurrentes, un monolito modular en Azure es suficiente y más pragmático que una arquitectura distribuida compleja.
  • Ajuste al dominio
    La funcionalidad gira alrededor de un proceso central de vacaciones y aprobaciones, por lo que conviene mantener una única aplicación con módulos internos bien separados.
  • Integración desacoplada
    Como no se exige tiempo real, las integraciones con Active Directory y ServiceNow deben resolverse mediante sincronización programada, reduciendo dependencia operativa de sistemas externos durante el uso diario.
  • Escalabilidad estacional
    El despliegue en Azure permite escalar horizontal o verticalmente en periodos de alta demanda, alineándose con el uso estacional indicado y con la necesidad de optimizar costes cuando el uso sea bajo.
  • Mantenibilidad
    Separar presentación, negocio, integración y persistencia facilita evolucionar reglas ambiguas que todavía deben aclararse, como delegación, definición exacta de responsables, umbrales de sobresolicitación o alcance de la jerarquía organizativa.
  • Experiencia de usuario
    El uso de Vue encaja bien con los requisitos de visualización de calendarios, periodos sobresolicitados y consulta sencilla por responsables.
  • Evolución futura
    La modularidad permite incorporar después capacidades como tarjetas adaptativas sin rediseñar la solución completa.
  • Uso exclusivo departamental
    La solución puede configurarse para un único departamento, tal como se indica, sin impedir una futura extensión si el alcance cambia.

5.4 Riesgos y Mitigaciones

  • Ambigüedad en datos de Active Directory
    Riesgo: no está definido qué información exacta de estructura organizativa debe obtenerse ni su alcance.
    Mitigación: definir un contrato de integración mínimo antes del diseño detallado, incluyendo atributos, frecuencia de carga y reglas de correspondencia con usuarios y responsables.
  • Ambigüedad en ServiceNow
    Riesgo: no está completamente cerrado qué datos de pertenencia departamental se obtienen ni cómo se enviará el listado de vacaciones aprobadas.
    Mitigación: acordar formato, frecuencia, mecanismo de intercambio y criterios de inclusión antes de construir la integración.
  • Reglas de aprobación incompletas
    Riesgo: existen requisitos sobre aprobación por proyecto, por departamento y por varios responsables, pero faltan detalles de precedencia y número de aprobadores.
    Mitigación: modelar el flujo de aprobación como configurable y validar con negocio las variantes antes de la implementación final.
  • Delegación poco definida
    Riesgo: no están claras las condiciones y alcance de la delegación de aprobadores.
    Mitigación: aislar esta lógica en el dominio y parametrizarla para evitar cambios invasivos.
  • Conceptos funcionales subjetivos
    Riesgo: expresiones como “muy visual”, “de manera sencilla” o “fácilmente” no son verificables.
    Mitigación: traducirlas a criterios concretos de interfaz y validarlas mediante prototipos de la aplicación web.
  • Picos estacionales de uso
    Riesgo: la demanda puede concentrarse en campañas concretas.
    Mitigación: desplegar en Azure con capacidad de escalado y monitorización, y dimensionar pruebas de carga al menos para el objetivo conocido de 500 usuarios concurrentes.
  • Dependencia de sistemas externos
    Riesgo: caídas o cambios en Active Directory, ServiceNow, correo o Teams pueden afectar el proceso.
    Mitigación: usar adaptadores desacoplados, reintentos, trazabilidad de errores y procesamiento batch nocturno para reducir impacto operativo.
  • Posible crecimiento de alcance
    Riesgo: se menciona interés de otros departamentos, aunque no es requisito actual.
    Mitigación: mantener diseño modular y parametrizable, pero sin sobredimensionar la primera versión.
