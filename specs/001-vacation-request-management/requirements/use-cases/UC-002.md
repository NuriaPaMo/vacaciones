# Use Case: Track Request Status

## Brief Description

An authenticated employee navigates to "My Requests" to view all their vacation requests with
current status, filter by status, sort by date, and drill into individual request details to see
the full status transition timeline.

## Stakeholders and Interests

| Stakeholder        | Interest                                                  |
| ------------------ | --------------------------------------------------------- |
| Employee           | Immediately know whether requests are approved/rejected   |
| Project Manager    | Indirectly: ensures employees don't pester PMs for status |
| System             | Serve accurate, up-to-date status within 2 seconds        |

## Preconditions

1. Employee is authenticated via Entra ID
2. Employee has previously submitted at least one vacation request

## Postconditions (Success Guarantees)

1. Employee sees accurate, up-to-date list of all their requests
2. Status timeline shows all state transitions with timestamps and actors

## Triggers

- Employee clicks "My Requests" in the navigation menu
- Employee clicks a notification link that deep-links to request status

---

## Main Success Scenario (Basic Flow)

| Step | Actor          | System                                                         |
| ---- | -------------- | -------------------------------------------------------------- |
| 1    | Employee navigates to "My Requests" |                                               |
| 2    |                | System fetches all vacation requests owned by the employee     |
| 3    |                | System renders list ordered by submission date (newest first)  |
| 4    |                | Each row shows: dates, total days, status (color-coded), submission date |
| 5    | Employee reviews the list |                                                         |
| 6    | Employee clicks on a specific request to view details |                               |
| 7    |                | System fetches StatusTransition records for the request        |
| 8    |                | System renders the status timeline (who acted, when, reason)   |

### Detailed Steps

**Step 4 — Status Color Coding**

- Pending → yellow/orange badge
- Approved → green badge
- Rejected → red badge
- Cancelled → grey badge

**Step 8 — Status Timeline**

Each transition shows:
- From status → To status
- Actor (employee name or "System")
- Timestamp (localized)
- Reason (for rejection/cancellation)

## Extensions (Alternative Flows)

### 2a. No Requests Exist

| Step  | Actor          | System                                                      |
| ----- | -------------- | ----------------------------------------------------------- |
| 2a.1  |                | System returns empty list                                   |
| 2a.2  |                | System shows empty state: "No vacation requests yet. Submit your first request." |

### 5a. Employee Filters by Status

| Step  | Actor                         | System                                          |
| ----- | ----------------------------- | ----------------------------------------------- |
| 5a.1  | Employee selects status filter (e.g., "Approved") |                               |
| 5a.2  |                               | System filters the list to show only matching requests |
| 5a.3  | Employee reviews filtered results |                                             |

### 5b. Employee Searches by Date Range

| Step  | Actor                         | System                                          |
| ----- | ----------------------------- | ----------------------------------------------- |
| 5b.1  | Employee sets date range filter |                                               |
| 5b.2  |                               | System shows only requests overlapping that range |

### \*a. System Unavailable

| Step  | Actor          | System                                                      |
| ----- | -------------- | ----------------------------------------------------------- |
| \*a.1 |                | System returns 503; frontend shows error message            |

## Special Requirements

- **Performance**: Page load < 2 seconds; list must render even with 20+ requests
- **Security**: Employee can only see their own requests (no cross-user access)
- **Audit**: Read access is not logged (read-only operation)

## Technology and Data Variations

- **Pagination**: List paginates at 20 items per page
- **Sort**: Default newest first; user can toggle to oldest first

## Frequency of Occurrence

- Expected: ~5 views/employee/month = ~2,500 page views/month
- Peak: day after a batch approval run
